# runany.dev Blog Post Template

Use this file as a human-facing reference for new blog posts in `apps/web/src/content/blog/`. It is not loaded by Astro at runtime and is not a generator input.

For GitHub Trending tool posts, prefer the Codex skill at `.codex/skills/github-trending-tool-blog/SKILL.md`; the agent should read the repo README/docs and write a repo-specific article instead of filling this template mechanically.

**Filename convention (SORTING — important):**
Filename format: `YYYY-MM-DD-[slug].mdx`

The filename MUST start with a date timestamp (YYYY-MM-DD) for automatic chronological sorting. The slug portion after the timestamp is the actual blog post slug — this is what appears in the URL.

```
2026-05-28-frigade-product-onboarding.mdx  →  URL: /blog/frigade-product-onboarding/
2026-05-27-agentmesh-multi-agent-setup.mdx  →  URL: /blog/agentmesh-multi-agent-setup/
```

The sorting logic strips the `YYYY-MM-DD-` prefix before generating the URL slug, so filenames with timestamps sort correctly by date while preserving the clean URL slug. **Do not include spaces, only hyphens.**

| `ai-setup` | AI tools, LLM setup, local inference |
| `tutorial` | Step-by-step how-to guides |
| `dev-tools` | Developer tools, editors, CLIs |

## Standard Article Structure

```mdx
## TL;DR

> **TL;DR:** One specific sentence that explains what the reader will learn or decide.

## Source and Accuracy Notes

Explain what official docs, repo, release notes, or tests the article is based on. Keep this reader-facing; do not include internal writing rules.

## What Is [Topic]?

Explain the tool, project, or concept in practical terms. Include who it is for, what problem it solves, and what it is not.

## Why It Matters

Give context, tradeoffs, and when the reader should care. Avoid generic hype.

## Prerequisites

- Required OS, runtime, account, API key, hardware, or prior knowledge
- Exact versions only when the source docs require them

## Setup or Workflow

### Step 1: Specific task name

Explain the step and why it matters.

```bash
# Use real documented commands only
echo "example"
```

### Step 2: Specific task name

Continue with concrete, source-backed instructions.

## Deeper Analysis

Explain architecture, limitations, hidden tradeoffs, production readiness, security, cost, or migration concerns.

## Practical Evaluation Checklist

- Concrete check tied to the topic
- Concrete check tied to setup/config
- Concrete check tied to risk or adoption

## Security Notes

Mention relevant risks such as shell access, file access, secrets, browser automation, third-party services, or private data.

## FAQ

**Q: Specific reader question?**
**A:** Direct answer grounded in the article source material.

**Q: Another specific reader question?**
**A:** Direct answer.

## Conclusion

Summarize the recommendation and the safest next step.
```

## Content Rules

- Write in English.
- TL;DR block is required and must start with `> **TL;DR:**`.
- Use H2 for main sections and H3 for sub-steps.
- Every fenced code block must include a language identifier.
- Use relative links for internal links, for example `/blog/other-post/`.
- Do not include internal agent rules, prompt instructions, generator notes, duplicate tracking, or thumbnail pipeline details in public articles.
- Do not invent commands, versions, ports, env vars, pricing, or claims.
- Avoid bot-style phrasing like `README says`, `README shows`, `according to the README`, and `the extracted sections`.
