> **TL;DR:** cloudflare-os is an Apache-2.0 agent workspace from Cloudflare, described as building on Workers so you can create documents, build apps, and run agents that have access to your company context and systems. It reached 10,581 stars in about five months, and the deployed product at os.cloudflare.app responds.

## What it says it is

The project description is short and concrete: an agent workspace built on Cloudflare Workers for creating documents, building apps, and running agents with your company context and systems. Three verbs, one platform. Nothing in that sentence needs unpacking, which is a good sign.

The interesting part is the framing. Most agent tooling in this category is a memory layer, a skill pack, or a wrapper around someone else's model. This one is a workspace, which implies a surface you open and work in, with Workers as the substrate underneath.

## The repository confirms the Workers claim

The description asks you to take the Workers dependency on faith. The repository layout settles it. The root of the tree contains a wrangler configuration file, which is the deployment manifest for Cloudflare Workers, alongside a Cloudflare config file and a pnpm workspace file with a packages directory. That is a Workers monorepo, not a library that happens to integrate.

The language breakdown is equally concentrated:


## Checking the deployment yourself

The homepage in the metadata is a real deployed URL, not a placeholder. It answers:

```bash
curl -sI https://os.cloudflare.app | head -1
```

The response came back `HTTP/2 200` with an HTML content type when this was written. That is not proof of anything about features, but it does confirm the product is live rather than announced.

## When it fits

Worth evaluating if you already run on Cloudflare and your agents need to touch internal systems. The description makes company context and systems part of the pitch, and Workers gives you a deployment target with a global edge and no server to manage, which is a reasonable default for glue code that runs occasionally.

It is also a useful reference even if you never deploy it. A public, vendor-maintained, Apache-2.0 workspace built on Workers is a working example of how this category is being structured, and the source is readable for that.

## When it does not

Skip it if you are not on Cloudflare. The whole design rests on Workers being the runtime, so porting means rewriting the substrate, not swapping a configuration value.

Weigh the vendor question too. The Apache-2.0 license is permissive and the code is auditable, but a workspace that holds company context is infrastructure you now depend on someone else's roadmap for. That can be exactly what you want. It should be a decision rather than a default.
