> **TL;DR:** OpenMausBot is a TypeScript project that gives an AI agent a virtual machine it can actually use, with a browser, files, and tools attached. It is Apache-2.0 licensed with an enterprise carve-out, runs on Docker, and sits at 7,534 stars after taking 1,199 new ones today.

## The repository is laid out like a shipped product

The root of the tree reads like a company codebase, not a weekend prototype. A pnpm monorepo with a Vite frontend, a separate server, shared code, and a docs app:

| Path | What it holds |
| --- | --- |
| `apps/docs` | Next.js documentation site |
| `server/` | Backend with colocated `*.test.ts` and `*.e2e.test.ts` files |
| `shared/` | Types and helpers used by both sides |
| `skills/` | Three packaged skills: `create-verification-skill`, `data-dashboards`, `phone-harness` |
| `third_party/` | Vendored dependencies including `browser`, `playwright-injected`, `cua-driver`, `cloudflared` |
| `Dockerfile` | 11 KB container build |
| `pnpm-workspace.yaml` | Workspace definition |

The `package.json` script list is the more telling part. There are separate build targets for `build:browser`, `build:cua:linux`, `build:cua:win`, `build:duckdb`, `build:speech`, `build:updater`, and `build:companion`, plus packaging scripts for macOS, Windows, and Linux. There are benchmark scripts for browser streaming, observation, and persistence. There are smoke tests for `cua-win`, `cua-x11-input`, and `deb-command`.

```bash
# The build matrix is the clearest statement of scope
pnpm build:browser
pnpm build:cua:linux
pnpm build:speech
pnpm package:mac
```

`third_party/` is worth a second look. Vendoring `playwright-injected` and `cua-driver` means the computer-use stack is not a thin API wrapper around someone else's browser automation. The `cua` prefix stands for computer use, and it appears in build targets, test targets, and the vendored driver directory.

## The licensing is not simply Apache-2.0

`LICENSING.md` is short enough to read in full and worth doing. The project is Apache-2.0 with a carve-out for the `enterprise/` directory. Everything under `enterprise/` is source-available under the OpenMausBot Enterprise License instead: you can read it, build it, and run it freely in development and test, but running those features in production requires a license key issued to your organization. Hosting it for third parties or white-labelling it needs a partner agreement.

There is a detail in that document that tells you how the project is maintained. Delete the `enterprise/` folder and the server reports `{"edition":"oss"}` while standalone operation stays unchanged. A dedicated CI job, the `open-source edition builds without enterprise/` check, proves the OSS build, the boot response, and the absent adapter factory. Hosted sign-in is the part that gets tested separately, through isolated hosted workspace tests covering sign-in and revocation paths.

So the open-source edition is not a promise, it is a build target.

## How to try it

There is no install command to copy from the README frontmatter. The tree gives you the honest options.

```bash
git clone https://github.com/milind-soni/OpenMausBot.git
cd OpenMausBot
pnpm install
pnpm dev:desktop
```

The `.env.example` file at the root is 886 bytes, which is small enough to read end to end before you start. It is the documented configuration surface. The `Dockerfile` at the root is the other route, and the `docker` topic tag means the container path is a first-class option rather than an afterthought.

## When to use it

The fit is a workflow where an agent needs a real machine instead of a tool call. A browser that renders, a filesystem that persists, a process that can be started. The `build:browser`, `build:cua:*`, and `build:speech` targets suggest the agent is expected to drive an actual desktop-like environment rather than emit structured JSON.

If you want the same behaviour under a different agent, the `claude-code` and `codex` topics suggest both are wired in. The skills directory ships a verification-skill creator, data dashboards, and a phone harness, so this is built for repeated multi-step runs where you want the agent to check its own work.

## When not to use it

The open issue count is 550 against 7,534 stars. That is a busy tracker on a repository that is two and a half months old. Read it before you commit, because the ratio suggests a lot of people are filing findings in parallel with the maintainers building.

Also note the enterprise carve-out. If the features you actually want live under `enterprise/`, your production use needs a license key, and the open-source build drops them. Verify which half of the tree your use case needs before planning around it.
