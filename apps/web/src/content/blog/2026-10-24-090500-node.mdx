> **TL;DR:** nodejs/node is the upstream source for the Node.js runtime, and it is the clearest place to see how a JavaScript runtime is put together: C++ under src/, JavaScript under lib/, vendored dependencies under deps/, and a test suite that pins the behaviour down. It is at 122,891 stars with 39,834 forks.

## What it is

The description is three words and a string of emoji: "Node.js JavaScript runtime". The owner is the nodejs organization and the homepage is nodejs.org, so this is the canonical repository rather than a fork or a mirror.

The numbers are the reason this repository keeps resurfacing on trending pages. 122,891 stars, 39,834 forks, 1,263 open issues and pull requests, and commits pushed on 2026-10-24. The repository record itself starts on 2014-11-26, which is when the project moved onto GitHub rather than the year the runtime first appeared.

GitHub reports the implementation language as JavaScript, which surprises people who assume the runtime is pure C++. The tree explains it: the engine is C++, but the tooling, the test harness and the benchmark scripts are JavaScript, and GitHub scores a repository by bytes.

## How the tree is organised

| Path | What it holds |
| --- | --- |
| `src/` | The C++ core: the runtime, the V8 binding layer, platform glue |
| `lib/` | JavaScript internals: modules, fs, net, streams, the bootstrap code |
| `deps/` | Vendored third-party dependencies |
| `test/` | The test suite, JavaScript tests plus native tests under `test/c++` |
| `tools/` | Repository tooling and lint configuration |
| `doc/` | API documentation sources |
| `typings/` | TypeScript type definitions |
| `benchmark/` | Performance measurement harnesses |

The build system sits alongside those directories rather than inside them. You get a `Makefile`, a `BSDmakefile`, `configure.py`, the `configure` wrapper, `node.gyp` with its `.gypi` and `.gni` files, `BUILD.gn`, and `vcbuild.bat` for Windows.

Contributor documents are unusually complete for a project of this size. `AGENTS.md`, `onboarding.md`, `glossary.md`, `GOVERNANCE.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`, `CHANGELOG.md` and `BUILDING.md` all sit at the root.

## Building it

`BUILDING.md` documents the Unix path, and the build scripts are in the tree next to it.

```bash
git clone https://github.com/nodejs/node.git
cd node
./configure
make -j8
./node -e "console.log(process.version)"
```

Windows has its own entry point. `vcbuild.bat` runs the build from a Visual Studio developer prompt.

```bat
vcbuild.bat
```

Android support is present too, through `android_configure.py` and the `android-patches` directory.

## Where to start reading

Three places answer most questions:

- `lib/` when you want to know what a JavaScript-facing API actually does, since the module system, `fs` and `net` are written in plain JavaScript here.
- `src/` when you need the boundary between JavaScript and C++, where the binding layer and the collector hooks live.
- `test/` when you want the specification, because the suite is the most complete statement of intended behaviour in the repository.

`AGENTS.md`, `onboarding.md` and `glossary.md` are the fastest way to get oriented, and `GOVERNANCE.md` explains how decisions are made in the project.

## When to read the source

Reach for it when a bug reproduces only on one version, when a native addon misbehaves at the C++ boundary, or when you want to know exactly what a Node.js API promises before you depend on it. The test suite is the part outsiders underuse, the same as in most language runtimes.

Skip it if you are building an application. Application code talks to the runtime through `node`, `npm` and the published API documentation, and none of that requires reading C++.
