> **TL;DR:** pstack-claude is a small MIT licensed JavaScript repository, 1,154 stars and 129 forks, whose job is porting. It carries Poteto's pstack agent workflows from Cursor primitives to six other harnesses, including Claude Code, Codex, Pi, OpenCode and Gemini.

## What the project actually is

Most trending agent repositories sell you a new assistant. This one sells you a translation layer, which is a rarer and more useful thing to see trend.

The description reads: Claude Code, Codex, Pi, OpenCode, Gemini, and Prime Agent versions of Poteto's pstack, with rigorous agent workflows and Cursor primitives translated for other harnesses. The word translated is doing real work there. The implicit claim is that a workflow system originally built for Cursor should be usable in the assistants most people actually run, and that pstack-claude is the port.

## Why a port is worth its own repository

Agent workflows are not portable by default. The primitives that make a workflow work, the way a tool is declared, the shape of a subagent definition, the assumptions about context and file layout, are all harness-specific in practice. A workflow that leans on Cursor's primitives does not run in Claude Code without work, and that work is repetitive across every workflow you want to move.

Centralising it in one repository turns a per-workflow porting problem into a single maintenance surface. The 1,154 stars against 129 forks is a narrower ratio than the video and CAD projects in today's batch, and that tracks with the nature of the thing. You install a plugin and use it, or you fork it and adapt it, rather than reading through the source to learn from it.

The `rigorous` in the description is a claim about the workflows themselves, and it is the one part you cannot check from metadata. Rigour in agent workflows is a matter of opinion about what a workflow ought to enforce.

## When to use it

The fit is narrow and clear. If you use Cursor workflows and have hit a wall running them elsewhere, or you want one disciplined workflow set to try in more than one assistant, this is the thing to look at. The MIT license removes any friction from adapting it to your own process.

If you are still choosing a harness, this is the wrong repo to start with. It assumes you already know pstack and want it somewhere specific. A wiki is enabled, so per-harness install notes are likely there, which is where you would confirm the actual package name and setup for whichever assistant you run.
