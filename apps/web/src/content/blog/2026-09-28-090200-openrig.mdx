> **TL;DR:** openrig is a multi-agent harness that runs Claude Code and Codex together as one system, per its own one-line description. The topic list spells out the shape: agent-harness, agent-orchestration, agent-skills, ai-coding, cli, codex-cli, and tmux, all under an Apache-2.0 license.

## What it is

Most agent tooling gives you one agent in one terminal. openrig's pitch is a different one: put Claude Code and Codex in the same system and orchestrate them together. The description says "as one system", and that phrase is doing the heavy lifting.

The topic list does more work here than the description does, and it is unusually complete for a project this young:

- `agent-harness` and `agent-orchestration` frame it as a control plane, not a thin wrapper
- `agent-skills` puts skills in as a first-class concept
- `claude-code` and `codex-cli` name both agents explicitly
- `multi-agent` and `multi-agent-systems` make the plural intent unambiguous
- `tmux` implies panes rather than a web UI
- `cli` and `ai-coding` place it firmly in terminal work

That tmux entry is the most informative one. Agent tooling built on tmux panes tends to be inspectable and scriptable, which is a meaningfully different choice from a closed graphical interface that hides each agent's state. You can look at every pane, scroll back through any agent's transcript, and reattach to a session after your laptop sleeps.

The interesting question, and one the description does not answer, is what happens when the two agents disagree. Two coding agents pointed at the same worktree will produce conflicting edits unless something arbitrates between them. If openrig partitions work by pane, that is simple and safe. If it lets both agents touch the same files, you want to understand the merge story before you trust it with anything you care about.

## When to use it

openrig fits if you already use more than one coding agent and have felt the cost of switching between them. The multi-agent framing pays off when tasks genuinely parallelise, for example one agent on tests while another works on the implementation.

It does not fit if a single agent with a solid workflow already covers your work. A harness that coordinates two agents adds process, and process you do not need is just overhead. The 51 open issues on a six-month-old project are worth a skim before you build a daily habit around it.
