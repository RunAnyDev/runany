> **TL;DR:** AiSOC is an open-source security operations center built around an AI agent that triages alerts. It fuses alerts from multiple sources, investigates them against MITRE ATT&CK, and records every agent step in a decision ledger you can replay. The project is MIT licensed, self-hostable, runs with no API keys, and ships an MCP server for Claude, Cursor and Continue. It was created in May 2026 and already has 6,263 stars.

## What it is

The repository description is unusually complete for a project six months old: "Open-source AI Security Operations Center: alert fusion, LLM-agent triage, MITRE ATT&CK investigation, and a replayable decision ledger for every agent step. Self-hostable, runs with no API keys, MIT licensed. Ships an MCP server for Claude, Cursor and Continue."

Read that as a list of five separate capabilities, because they are.

Alert fusion means several alert sources become one stream. Triage means the agent does the first-pass judgement on each alert instead of a human opening a ticket. ATT&CK investigation means the reasoning maps onto a known framework of adversary tactics rather than being free-form. The decision ledger is the record of how it reached each decision.

The topics are `agentic-ai`, `ai-security`, `alert-triage`, `blue-team` and `cybersecurity`. The blue-team tag tells you where the project sits on the defensive side of the house.

## The decision ledger is the part worth caring about

Most agent tooling tells you what an agent decided. Very little tells you why, in a form you can audit later.

AiSOC records every step the agent takes in a replayable ledger. For a security tool, that is the difference between a system you can put in front of an auditor and one you cannot. When a triage decision is wrong, or worse when it misses a real incident, the ledger is what you would use to work out where the reasoning went sideways.

This also changes the security conversation. An agent that touches production alerts is a privileged component. Being able to replay its reasoning on demand is how you justify that privilege.

## It runs with no API keys

"No API keys" is a load-bearing claim in that description, and it is the reason the project lists as self-hostable.

An AI SOC that needs a cloud LLM key has two problems. The alerts themselves may contain sensitive infrastructure detail, and sending them to a third-party API provider creates a data boundary you probably did not intend to cross in a security tool. AiSOC is built to run with models you host, so the reasoning stays inside your perimeter.

```bash
git clone https://github.com/beenuar/AiSOC.git
cd AiSOC
```

The project homepage in the metadata is beenuar.github.io/AiSOC, which is where the deployment documentation lives.

## The MCP server is the interesting integration

Shipping an MCP server for Claude, Cursor and Continue puts AiSOC in reach of the tools people already use. An analyst working in an editor can query triage state or pull an investigation without leaving the editor.

That matters for adoption. Security tooling often fails on workflow fit rather than capability, and an MCP surface is a way to say the tool does not require you to switch applications to use it.

## When it is not the right fit

AiSOC is not a SIEM and does not try to be one. It is an agent-driven triage layer, which means it assumes some alerting already exists upstream.

It is also not a replacement for a human analyst. Triage narrows a queue. Someone still has to run the incident response.

And if you are not self-hosting models, the "no API keys" property becomes less interesting, since you will be pointing it at a local inference setup either way.
