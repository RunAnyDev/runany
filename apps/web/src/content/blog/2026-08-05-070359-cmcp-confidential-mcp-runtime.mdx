## What Is cMCP?

Standard MCP runtimes evaluate tool-call policy in the same OS process as the agent itself — meaning a compromised process can bypass the policy engine, swap the policy bundle after approval, or rewrite the audit log after the fact. Software-only governance cannot close these gaps because the control plane runs where the governed process can reach it.

cMCP (Confidential MCP Runtime) moves policy enforcement into a hardware Trusted Execution Environment. Every tool call is intercepted, evaluated against a signed Cedar policy bundle inside the enclave, and enforced where the agent process cannot interfere. The output is a signed `TRACE Claim` — a tamper-evident record of every decision, hardware-attested when running on SEV-SNP, TDX, or TPM hardware.

Key capabilities shipped in the developer preview:

- MCP tool call interception via HTTP/SSE transport (stdio support planned for Phase 2)
- Cedar policy evaluation inside the TEE with hash-chained audit log
- `TRACE Claim` generation with hardware attestation in SEV-SNP and TDX modes
- `cmcp_verify` offline verifier that checks attestation without trusting the operator
- Three enforcement modes: `enforcing` (default), `advisory`, and `silent`
- No hardware required in software mode — works out of the box with `pip install cmcp-runtime`

## Setup Workflow

### Prerequisites

- Python 3.11 or later
- One of: SEV-SNP (AMD), TDX (Intel), or TPM (Azure Trusted Launch) for hardware attestation — software mode works without any special hardware

### Step 1: Install the Runtime

```bash
pip install cmcp-runtime
```

### Step 2: Start the Gateway in Software Mode

```bash
cmcp-runtime start
```

The gateway starts in software mode with no special hardware required. All policy evaluation happens in a separate process, and every `TRACE Claim` is signed in software. Hardware attestation (SEV-SNP, TDX, TPM) is probe-detected automatically when available.

### Step 3: Configure a Cedar Policy Bundle

cMCP evaluates incoming tool calls against a Cedar policy bundle. A minimal policy looks like this:

```json
{
  "principal": "user-123",
  "action": "mcp::tools::call",
  "resource": "salesforce::crm",
  "effect": "permit"
}
```

Apply it by pointing the gateway at a policy file:

```bash
cmcp-runtime set-policy --file ./policy.json
```

### Step 4: Point Your MCP Agent at the Gateway

Route your agent's MCP traffic through the cMCP gateway instead of directly to tools:

```bash
export MCP_SERVER_URL="http://localhost:8080"
# your agent now calls through cMCP
```

Every tool call is intercepted, evaluated inside the TEE against the loaded policy, and either allowed or blocked. A signed `TRACE Claim` is emitted for each decision.

### Step 5: Verify a Trace

Use the offline verifier to check a trace without trusting the operator:

```bash
cmcp_verify --trace <trace-file.json>
```

The verifier checks the attestation report independently — no trust in the gateway operator required when hardware attestation is active.

## How Attestation Works

When running on supported hardware, cMCP uses a hardware-rooted chain:

1. The gateway process loads inside the TEE and measures the policy bundle hash into the hardware attestation report before any code runs.
2. Every tool call is evaluated inside the enclave — the policy engine cannot be reached by the agent process.
3. A signed `TRACE Claim` records each decision. In hardware mode, this claim is signed by a key that never leaves the enclave.
4. The `cmcp_verify` tool checks the attestation report and validates the claim signature without trusting the operator.

Verified hardware attestation runs include SEV-SNP on Azure CVM (ECDSA-P384 report signature, VCEK chain to AMD ARK-Milan root) and GCP C3 Intel TDX DCAP v4 (PCK chain to pinned Intel SGX Root CA).

## Enforcement Modes

| Mode | Behavior |
|---|---|
| `enforcing` | Policy decisions are blocked/allowed in the TEE; denied calls return an error |
| `advisory` | Policy evaluation runs and logs decisions, but calls are not actually blocked |
| `silent` | Policy evaluation is skipped; all calls pass through with a warning in the trace |

Default is `enforcing`.

## Security Notes

- In software mode, the signing key is not hardware-protected. Hardware attestation requires SEV-SNP, TDX, or TPM hardware.
- The policy bundle is measured into the TEE attestation report at load time, so swapping it post-approval is detectable.
- The Cedar policy evaluator runs inside the enclave address space — a supply chain CVE in the evaluator still runs in the same enclave as the attacker, but the enclave boundary limits blast radius.
- TPM attestation certificate chain verification is partial (see STATUS.md: `ek_cert_chain` is unconditionally unverified on some Azure Trusted Launch configurations).

## FAQ

**Q: Does cMCP support stdio-based MCP servers?**
**A:** Not yet. The developer preview supports HTTP/SSE transport. Stdio bridge support is planned for Phase 2.

**Q: What happens when no hardware is available?**
**A:** cMCP falls back to software mode automatically. Policy evaluation still runs in a separate process for isolation, but the `TRACE Claim` is signed in software rather than hardware-attested.

**Q: Can I use cMCP with any MCP client or does it require a specific agent framework?**
**A:** cMCP acts as a transparent gateway. Any MCP client that can route through an HTTP endpoint can use it, provided the traffic uses the HTTP/SSE transport.

**Q: How does cMCP compare to a standard MCP server?**
**A:** A standard MCP server exposes tools to an agent. cMCP wraps that flow with a policy enforcement layer that can permit or deny individual tool calls based on Cedar policies, with a tamper-evident audit trail.

## Conclusion

cMCP addresses a real gap in MCP deployments: once an agent has access to tools, nothing in a standard MCP setup prevents it from calling those tools in ways the operator never intended. By moving policy enforcement into a TEE and emitting hardware-attested `TRACE Claims`, cMCP gives operators proof — not just trust — that their tool access policies were followed.

Install it with `pip install cmcp-runtime`, start with `cmcp-runtime start`, and point your agent at the gateway. No special hardware required to evaluate the model.
