> **TL;DR:** Xerj is a Rust search engine built for agents, claiming one-command indexing of code, docs, logs and PDFs plus 40x fewer tokens than grep. It is Apache-2.0 licensed with 5,728 stars, and the Elasticsearch compatibility is the part most likely to save you migration work.

## What it is

The pitch is token economics. An agent searching a codebase with `grep` and `sed` burns context on lines that turn out to be irrelevant. Xerj's claim is that autoindexing lets an agent retrieve targeted results instead, using 40x fewer tokens than grep for the same job.

That number is the repository's own claim, and no benchmark is cited in the GitHub metadata. Read it as a direction of travel rather than a measured figure.

One command is meant to index code, documentation, logs and PDFs, and the description names the jobs it targets: search, RAG, security audits and agent memory. Four different consumers of the same index is an unusual way to frame a search tool, and it is the most interesting part of the pitch.

## Elasticsearch compatible

This is the practical detail. If existing Elasticsearch clients can talk to it unchanged, you do not rewrite the search layer of an agent system to find out whether it works. You point the client somewhere else.

That is a much stronger compatibility claim than "implements a search API", and it is the reason to read further before weighing anything else in the description.

## How to try it

```bash
git clone https://github.com/xerj-org/xerj.git
cd xerj
```

Check how indexing is wired before pointing it at a large corpus. A 116 MB repository that indexes PDFs and logs is doing real work, and the storage profile matters more than the speed claim.

## When to use it

It fits when an agent is reading more code and documents than fit comfortably in context and your current approach is grep. Security audit workflows are the clearest case, since the index is doing the narrowing instead of the agent reading its way through every file.

The Elasticsearch compatibility makes it cheap to trial inside an existing stack, which is unusual for a project this young and lowers the cost of finding out whether the token savings hold up on your own data.

## When not to use it

Skip it on a small repository. Indexing has a floor, and across a few hundred files grep is faster with nothing to maintain.

A three month old Rust project from a user account carries a different risk profile than an established engine. Pin your version and read the release history before wiring it into anything you cannot roll back easily.
