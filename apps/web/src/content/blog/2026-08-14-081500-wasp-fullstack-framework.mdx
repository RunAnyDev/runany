## What Is Wasp?

Wasp (Web App SPecification) is an open-source full-stack framework for building React and Node.js web applications. Instead of wiring together auth, jobs, email, and deployment manually — or relying on a third-party PaaS — Wasp provides a high-level declarative specification layer (the `.wasp.ts` file) that drives code generation for both the client and server.

The official tagline on the project page reads:

> "The batteries-included full-stack framework for the AI era. Develop JS/TS web apps (React, Node.js, and Prisma) using declarative spec files."

Wasp is not a React meta-framework (like Next.js or Remix). It generates a Rails/Laravel-style monolith where the spec file describes the app's full-stack behavior, and Wasp's CLI compiles it down to a working project using React (client), Node/Express (server), and Prisma (database).

## Key Features

The feature set described here is verified from the [official website](https://wasp.sh) and [GitHub README](https://github.com/wasp-lang/wasp).

### Declarative Full-Stack Spec

The core of Wasp is a `main.wasp.ts` file where you declare routes, pages, auth, jobs, and email in a single DSL-like syntax. Wasp then generates the corresponding React components, Express routes, and Prisma schema. The README gives this example:

```typescript
// main.wasp.ts
route "/tasks" { component: TasksPage }
page TasksPage { component: Import(Tasks) }
```

The generated code uses React Router for the client and Express for the server, with Prisma handling the database layer.

### Built-In Auth

Wasp ships authentication out of the box — username/password, Google OAuth, email + password reset, and (per the website) "Magic Link" support. The auth UI components are also auto-generated.

### Async Jobs

Long-running background tasks (email sending, webhook processing, report generation) are declared in the spec and run via a built-in job runner backed by a PostgreSQL queue. You write a plain Node.js function; Wasp handles scheduling and retry.

### Email

Transactional email is declared in the spec and sent through a configurable provider (currently SMTP or SendGrid). The email template lives in the spec, not scattered across your codebase.

### Deploy Anywhere

Because Wasp compiles to a standard Node.js/Express server, you can deploy to any VPS, Docker host, or platform that runs Node. There is no proprietary runtime. The project also maintains official deployment templates for Railway, Render, and Fly.io.

### AI Integration

The Wasp website explicitly positions the framework for the "AI era" — Wasp's GitHub topics include `ai` alongside `javascript`, `node`, `react`, and `prisma`. The framework's architecture separates the AI agent prompt/behavior definition from the actual web app, making it straightforward to drop in an LLM provider without restructuring the app.

## Setup Workflow

### Prerequisites

- Node.js 18 or later
- npm, pnpm, or yarn
- (Optional) Docker for local database

### Install the Wasp CLI

```bash
npm install -g wasp
```

### Create a New Project

```bash
wasp new my-app
cd my-app
```

The `wasp new` command scaffolds a project with a `main.wasp.ts` spec file and the necessary React/Node/Prisma structure.

### Run Locally

```bash
wasp db migrate-dev   # Apply Prisma migrations
wasp start            # Start dev server
```

`wasp start` runs both the React dev server (client) and the Node/Express API server concurrently. The client is served on port 3000 by default, with the API on a separate port.

### Add Auth

In `main.wasp.ts`:

```typescript
auth: {
  userEntity: User,
  methods: {
    email: {},
    google: {},
  },
  session: {
    expiresIn: 7 * 60 * 60 * 24, // 7 days in seconds
  },
}
```

Run `wasp db migrate-dev` again to apply auth-related schema changes, then the auth routes and pages are auto-generated.

### Deploy

Build for production:

```bash
wasp build
```

The output is a standard Node.js server and a React static bundle. Deploy with Docker:

```bash
docker build -t my-wasp-app .
docker run -p 3000:3000 my-wasp-app
```

Or use the [deployment guides](https://wasp.sh/docs) for Railway, Render, or Fly.io.

## Architecture Overview

Wasp follows a "onion" architecture pattern described on the official site:

- **Spec Layer (outer)** — The `main.wasp.ts` file is the single source of truth for routes, auth, jobs, and email.
- **Generated Code** — Wasp generates React components (using React Router), Express routes, and Prisma schema from the spec.
- **User Code** — You write React components and Node.js operations; Wasp's CLI manages the glue.

The spec layer intentionally constrains what you can express, but for the 80% case (auth, jobs, email, basic CRUD), you never touch the generated code directly.

## Security Notes

- Auth uses `bcrypt` for password hashing and JWTs for session tokens (verified from docs).
- All auth flows are server-side; Wasp does not store passwords in plaintext.
- The PostgreSQL-backed job queue uses standard advisory locks for concurrency.
- For production deployments, environment variables (`DATABASE_URL`, `APP_SECRET`) must be set — the `.env.example` is generated by `wasp new`.

## FAQ

**Q: How is Wasp different from Next.js or Remix?**
**A:** Next.js and Remix are React meta-frameworks — they handle the server/routing layer but you still wire up auth, database models, email, and background jobs yourself. Wasp generates the entire server-side stack from a declarative spec, including auth, jobs, and email, with no third-party service required.

**Q: Can I use Wasp with a database other than PostgreSQL?**
**A:** Wasp uses Prisma as its ORM. In development, SQLite is supported. In production, PostgreSQL is recommended and officially supported. MySQL and other databases work through Prisma but may have limited Wasp-specific tooling.

**Q: Is Wasp suitable for production use?**
**A:** Yes — companies like Hireveld and Microinfluencer Club run Wasp apps in production (shown on the official showcase). Wasp is at beta/v1 stage as of 2026, with a stable spec format and active maintenance.

**Q: Does Wasp lock me into its framework?**
**A:** No. Because Wasp compiles to plain React + Node.js + Prisma, you can always extract the generated code and drop the Wasp CLI. There is no proprietary runtime or hidden abstraction layer at the server level.

**Q: How does Wasp handle AI/agent features?**
**A:** Wasp has no built-in AI provider — you integrate your preferred LLM (OpenAI, Anthropic, local model) as a standard Node.js dependency. The framework's spec layer keeps the AI agent's prompt and behavior cleanly separated from the web app's UI and data layer.

## Conclusion

Wasp fills a specific gap in the TypeScript full-stack landscape: between the low-level flexibility of Next.js/Remix (where you wire everything yourself) and the high-level abstraction of Firebase/Supabase (where you pay for and depend on a third-party service). If you want a batteries-included server in the Rails/Laravel tradition — but with TypeScript, React, and a declarative spec — Wasp is worth a look.

The 18.6k GitHub stars, MIT license, and active Discord community suggest it is not a weekend project. The [official showcase](https://wasp.sh#showcases) lists real production apps. For developers who want to move fast on a full-stack TypeScript project without stitching together five separate services, Wasp's approach is genuinely differentiated.
