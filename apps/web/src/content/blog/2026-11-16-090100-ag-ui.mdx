> **TL;DR:** AG-UI is an open, event-based protocol that defines how an AI agent and a user-facing frontend talk to each other. It sits next to MCP, which gives agents tools, and A2A, which lets agents talk to other agents. The protocol ships about 16 event types, a reference HTTP implementation, and SDKs for TypeScript, Python, .NET plus eight community languages, with integrations for LangChain, CrewAI, Google ADK, Mastra, AWS Bedrock AgentCore and more. The repository has 17,932 stars, 1,821 forks and an MIT license.

## What AG-UI is

The repo at https://github.com/ag-ui-protocol/ag-ui describes itself as the Agent-User Interaction Protocol, an open, lightweight, event-based standard for connecting agents to applications that a person actually looks at. The protocol was born at CopilotKit out of real in-app agent work, then opened up as a standalone specification.

The interesting part is what problem it fills. Traditional frontend-backend assumptions break badly when an agent sits on the other side of the wire. The docs at https://docs.ag-ui.com/introduction spell out why:

- Agents are long-running and stream intermediate work across multi-turn sessions.
- Agents are nondeterministic and can drive application UI nondeterministically.
- Agents mix structured and unstructured IO, text and voice alongside tool calls and state updates.
- Agents need compositional interaction, calling sub-agents often recursively.

A REST or GraphQL endpoint does not model any of that. AG-UI layers an event stream over HTTP and WebSockets so the frontend can watch a run unfold rather than wait for a response to arrive.

## Where it sits in the protocol stack

The project positions itself as one of three complementary open agentic protocols, and the distinction matters if you are choosing where to invest.

| Layer | Protocol | Purpose |
|---|---|---|
| Agent to user | AG-UI | The open, event-based standard that connects agents to user-facing applications |
| Agent to tools and data | MCP | Lets agents securely connect to external systems, tools, workflows and data sources |
| Agent to agent | A2A | Defines how agents coordinate and share work across distributed agentic systems |

In practice MCP is how your agent calls a database or a GitHub API, A2A is how your agent delegates to another agent, and AG-UI is how the result of all that streaming back into a React app so a human can watch and interrupt it.

The protocol also ships a flexible middleware layer. It works with any event transport (SSE, WebSockets, webhooks) and it allows loose event format matching, which is the part that makes cross-vendor interoperability practical rather than aspirational. Alongside it there is a reference HTTP implementation and a default connector so a team can get a running setup before writing any integration code.

## How the event model works

Events are the fundamental unit of communication between agents and frontends, and the event catalogue at https://docs.ag-ui.com/concepts/events is where most of the practical detail lives. Every event carries a base property set: a `type` identifier, an optional `timestamp`, an optional `rawEvent` for the original payload if something transformed it, and an optional `metadata` object.

| Event group | What it carries |
|---|---|
| Lifecycle | `RunStarted`, `RunFinished`, `RunError`, plus optional `StepStarted` and `StepFinished` pairs |
| Text messages | `TextMessageStart`, `TextMessageContent`, `TextMessageEnd`, and the convenience `TextMessageChunk` |
| Tool calls | `ToolCallStart`, `ToolCallArgs`, `ToolCallEnd`, and `ToolCallResult` |
| State | `StateSnapshot` and `StateDelta` for shared agent and application state |

Two details are worth pulling out. First, `RunStarted` and either `RunFinished` or `RunError` are mandatory, so they form the boundaries of every run, which is what lets a frontend drive loading indicators and error recovery without guesswork. Step events are optional and can repeat.

Second, text streaming is a three-event dance. `TextMessageStart` establishes a `messageId` and a role, each `TextMessageContent` carries a `delta` chunk that the frontend appends, and `TextMessageEnd` closes it. If you would rather not manage that yourself, `TextMessageChunk` expands automatically into the Start, Content and End triad, and the client stream transformer handles the rest.

Metadata is worth understanding too. It is an open, by-key object declared once on the base event, so every event type carries it, and consumers merge it into the message the event builds with the last write winning. That is what allows a producer to attach token usage on the final event of a message rather than having to know the total in advance.

## Trying it yourself

The project ships a scaffolding CLI. From the project repository the one-liner is:

```bash
npx create-ag-ui-app my-agent-app
```

The documentation at https://docs.ag-ui.com/quickstart/applications shows the same CLI in its latest form, followed by the standard dev server:

```bash
npx create-ag-ui-app@latest
```

```bash
npm run dev
```

For the CopilotKit example the docs point you at http://localhost:3000 to see the app running. There is also a hosted playground at https://dojo.ag-ui.com/, which the project calls the AG-UI Dojo. Each example there is deliberately small, roughly 50 to 200 lines of code, and every one of them ships with a preview, the source and a walkthrough. That is a much faster way to understand shared state or tool-based generative UI than reading a specification cold.

## The integration surface

The breadth of integrations is the strongest signal of adoption here. The repository tracks each platform as a partnership, first party or community integration, and the list covers most of the agent framework landscape.

| Integration | Tier | Notes |
|---|---|---|
| LangChain, CrewAI | Partnership | Where AG-UI started, alongside CopilotKit |
| Google ADK, Google Antigravity, Microsoft Agent Framework | First party | Full docs and Dojo demos |
| AWS Strands Agents, Amazon Bedrock AgentCore | First party | Infrastructure and deployment targets |
| Mastra, Pydantic AI, Agno, LlamaIndex, AG2 | First party | Each with docs and demos |
| Claude Agent SDK, Claude Managed Agents SDK, OpenAI Agents SDK, Cloudflare Agents | Community | Demos and integration directories in the repo |

SDKs cover TypeScript, Python and .NET as the documented first-class set, with Kotlin, Go, Dart, Java, Rust, Ruby, C++ and Nim maintained in community directories. Nim, Flowise and Langflow are marked in progress. On the client side the protocol lists CopilotKit, terminal and agent clients, chat platforms including Slack and Microsoft Teams, React Native, and OpenBot.

There is a specification track too, with Oracle Agent Spec listed as supported, and generative UI work tracked through A2UI and MCP Apps.

## Limits worth knowing

AG-UI is a protocol plus reference implementation, not a product you deploy as-is. A few honest caveats.

The repository was created on 2026-05-07 and is moving fast, with 593 open issues at the time of writing. Several SDKs are community contributions rather than core code, so quality varies by language, and three SDKs are still listed as in progress.

The protocol also does not solve the hard parts of agent UX for you. It standardises the plumbing: event shapes, transports, lifecycle boundaries, state synchronisation. What your interface does when the agent asks for approval, or how you render a tool call that takes forty seconds, is still your product decision. The Dojo demonstrates patterns, it does not pick them for you.

Finally, the middleware layer that does the loose event matching is where you will spend time when your backend does not emit AG-UI events natively. The docs have a dedicated debugging tutorial at https://docs.ag-ui.com/tutorials/debugging if you hit that path.

## When to reach for it

AG-UI makes sense when you are building a user-facing agent surface and you want the frontend contract to be portable across backends. If you are swapping between a hosted agent API, a local model runtime and a self-hosted framework, a shared event contract is the difference between a rewrite and a config change.

It is less useful if you only need tool calling, in which case MCP is the layer you want and AG-UI adds a dependency. It is also the wrong tool if you are building a batch job or a plain API surface with no human in the loop, because the protocol is built around streaming interaction with a person watching.

If you want to see the shape of the thing before committing, open a Dojo example for the feature you care about and read the 50 lines of code behind it.
