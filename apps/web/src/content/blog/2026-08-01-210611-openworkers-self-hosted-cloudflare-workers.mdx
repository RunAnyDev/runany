## What Is OpenWorkers?

OpenWorkers is a self-hosted runtime for JavaScript workers that replicates the Cloudflare Workers API surface. It was launched on Hacker News in mid-2026 and reached 500 points.

From the README:

> OpenWorkers is a runtime for running javascript code in a serverless environment. This runner manages instances of OpenWorkers Runtime.

The core is written in Rust. It supports multiple JavaScript engine backends, with **V8 as the recommended runtime** for production use. Alternative engines (QuickJS, Boa, JavaScriptCore, Deno) are available but experimental.

### Architecture Overview

The full self-hosted stack includes:

| Component | Role |
|---|---|
| `openworkers-runner` | V8 isolate runtime — executes worker JavaScript |
| `openworkers-api` | REST API for managing workers |
| `openworkers-scheduler` | Cron job scheduler (optional) |
| `openworkers-logs` | Log aggregator (optional) |
| `postgate` | Multi-tenant HTTP proxy for PostgreSQL with SQL validation |
| PostgreSQL | Database for worker state and data |
| NATS | Message queue for inter-worker communication |

Workers communicate with each other via NATS, and access the database through Postgate, which validates SQL before execution to prevent injection in multi-tenant scenarios.

## Setup Workflow

### Prerequisites

- Rust toolchain (for building from source)
- PostgreSQL
- NATS server
- Docker (optional, for containerized deployment)

### Step 1: Build the Runner

The runner supports multiple JavaScript runtime backends via Cargo feature flags.

```bash
# V8 runtime (recommended for production)
cargo build --release --features v8

# Alternative runtimes (experimental)
cargo build --release --features quickjs   # QuickJS - lightweight
cargo build --release --features boa       # Boa - pure Rust
cargo build --release --features jsc      # JavaScriptCore (Apple platforms)
cargo build --release --features deno      # Deno - legacy
```

V8 is the recommended backend because it offers full Web API support and the best performance characteristics for production use.

### Step 2: Prepare the Database

```sql
CREATE USER openworkers WITH PASSWORD 'your_password';
CREATE DATABASE openworkers WITH OWNER openworkers;
```

### Step 3: Configure Environment Variables

```bash
DATABASE_URL='postgres://openworkers:your_password@localhost:5432/openworkers'
NATS_SERVERS='nats://localhost:4222'
```

Additional networking and runtime options:

| Variable | Default | Description |
|---|---|---|
| `WORKER_DOMAINS` | `workers.rocks` | Comma-separated worker domains for internal routing |
| `HTTP_POOL_MAX_IDLE_PER_HOST` | `100` | Max idle HTTP connections per host for worker `fetch()` |
| `V8_EXECUTE` | `PINNED` | Execution mode: `PINNED`, `POOLED`, or `ONESHOT` |
| `WORKER_POOL_SIZE` | CPU cores | Number of V8 worker threads |
| `SNAPSHOT_CACHE_MAX` | `5000` | Max entries in in-memory code cache LRU |

### Step 4: Choose an Execution Mode

OpenWorkers supports three V8 execution strategies:

**PINNED (default):** Thread-local isolate pools keyed by tenant. Each thread maintains its own pool of V8 isolates. Zero cross-thread contention. New V8 context per request so no JS state leaks between requests. Includes configurable backpressure via per-thread queue.

**POOLED:** Single global LRU pool shared across all threads, protected by a mutex. Simpler but higher contention under load.

**ONESHOT:** Fresh V8 isolate per request, destroyed after each response. Adds ~1–2ms overhead per request. Useful for debugging or as a workaround for a V8 SIGSEGV issue in containerized environments (`SEGV_PKUERR` on PINNED/POOLED modes — see [openworkers-runner#2](https://github.com/openworkers/openworkers-runner/issues/2)).

### Step 5: Docker Compose Deployment

The infrastructure repo includes a Docker Compose setup:

```bash
# Clone and start
git clone https://github.com/openworkers/openworkers-infra
cd openworkers-infra
docker compose up -d
```

This brings up the full stack: API, runner, dashboard, PostgreSQL, NATS, Postgate, and optional log/scheduler services.

## Deeper Analysis

### Database Access Pattern

Unlike Cloudflare Workers (which use Workers KV and D1), OpenWorkers provides a direct `env.DB.query(sql)` binding. Under the hood:

1. Worker code calls `env.DB.query(sql)`
2. The Rust runner invokes `postgate::execute(sql)` via the Postgate library
3. Postgate validates the SQL and executes against PostgreSQL
4. Result flows back through the runner to the worker

Postgate HTTP endpoint is only used for admin operations by the OpenWorkers API itself — worker database calls use the library interface directly.

### Optional Services

The `logs` and `scheduler` services are not required for the core runtime but add functionality:

- **`openworkers-logs`**: Aggregates worker logs for debugging and monitoring
- **`openworkers-scheduler`**: Provides cron job support within the worker environment

Both workers can run as actual Cloudflare Workers (or any Workers-compatible runtime) themselves if you want a minimal footprint.

### CLI

The CLI manages database migrations and worker lifecycle:

```bash
openworkers-cli migrate
openworkers-cli worker:deploy my-worker --script=./dist/index.js
```

## Practical Evaluation Checklist

- ✅ V8-based isolation (same engine as Cloudflare Workers)
- ✅ Multi-tenant PostgreSQL access with SQL validation via Postgate
- ✅ NATS for inter-worker messaging
- ✅ Three execution modes for different performance/tradeoff needs
- ✅ OpenTelemetry support (`OTLP_ENDPOINT` env var)
- ✅ Docker Compose for one-line self-hosted deployment
- ⚠️ No built-in rate limiting or KV-like storage (bring your own)
- ⚠️ Actively developed — APIs may change

## Security Notes

- Postgate validates all SQL before execution, mitigating injection in multi-tenant setups
- V8 contexts are created fresh per request — no JS state bleeds between requests
- Database credentials are injected via environment variables, not hardcoded
- For production: run the runner and database on isolated networks; NATS should be ACL-controlled

## FAQ

**Q: How does this compare to Cloudflare Workers?**
**A:** OpenWorkers replicates the Workers API surface so existing worker code often works with minimal modification. The key difference is you own the infrastructure. There is no equivalent to Workers KV, D1, or Durable Objects out of the box — OpenWorkers focuses on the runtime itself.

**Q: Can I run this on a single VPS?**
**A:** Yes, the Docker Compose stack runs on a single machine. For production under load, you will want separate instances for the database, NATS, and the runner, plus a load balancer in front of multiple runner instances.

**Q: Does it support the full Workers API?**
**A:** It aims to replicate the core APIs (`fetch`, `Request`, `Response`, `env.DB`). Web Crypto, streams, and other standard Web APIs are supported through V8. Check the [openworkers-runner README](https://github.com/openworkers/openworkers-runner) for the current API coverage status.

**Q: Is there a hosted version?**
**A:** Yes — openworkers.com offers a hosted SaaS version. The open-source version is what this post covers.

## Conclusion

OpenWorkers fills a specific gap: you want the Cloudflare Workers developer experience (fast cold starts, V8 isolate isolation, simple `fetch`-based routing) but need to run it on your own infrastructure for compliance, cost, or control reasons. The Rust-based runner is well-structured, the Postgate SQL validation layer is a thoughtful touch for multi-tenant database access, and the Docker Compose setup makes local experimentation easy.

If you have been looking for a self-hosted Workers-compatible runtime, this is one to evaluate seriously.
