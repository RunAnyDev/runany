> **TL;DR:** Expo publishes a collection of agent skills covering its SDK and its Application Services, grouped through a skills.sh manifest and shipped with an evaluation harness. It has 3,610 stars under the MIT license.

## What it is

The description splits the scope in two: skills for working with Expo projects, and skills for Expo Application Services, which is the hosted platform side of the business.

The repository follows the skills directory convention that has become common across agent tooling, with an interesting twist. There is no `skills/` directory at the root. Instead there are `plugins/`, holding `expo` and `expo-experiments`, and a `skills.sh.json` manifest at the top level that describes how the skills are grouped.

```text
.agents/
.claude-plugin/
.claude/
.eas/
.github/
assets/
eval-harness/
plugins/
├── expo/
└── expo-experiments/
scripts/
tests/
skills.sh.json
app.json
package.json
AGENTS.md
CLAUDE.md
```

## The manifest is the interesting file

`skills.sh.json` follows a published schema, and it carries a `groupings` array. The first group is titled "Framework (open source)" and its description reads: "Free, open-source Expo SDK and React Native skills: UI, navigation, styling, data fetching, native modules, DOM, examples, and SDK upgrades."

The skill list under it names the topics directly:

```text
expo-overview
expo-project-structure
expo-router
expo-animation
expo-native-ui
expo-design-system
expo-ui
expo-data-fetching
expo-dom
expo-web-to-native
expo-module
expo-brownfield
expo-dev-client
```

The title of that group is doing some work. "Framework (open source)" distinguishes the free SDK from the rest of the groupings, which is a good signal that the paid Application Services side is covered separately. The `.eas/` directory at the root is the EAS side of the repository.

A skills.sh manifest with grouping metadata is how a skill collection gets browsed by directory rather than by cloning and reading, and the `notGrouped` setting shows the author thought about how ungrouped skills should be displayed.

## An eval harness is the part most collections skip

The `eval-harness/` and `tests/` directories exist next to the skills themselves. That is worth pausing on, because a skill is a prompt, and prompts regress silently. Nothing breaks, the model just gets worse at the task, and nobody notices because nothing failed.

A harness turns "this skill seems to help" into something you can run repeatedly and compare. If you build skills for your own team, this directory is the piece to copy.

There is also `app.json`, which ties the collection to an Expo app, and a `.gitmodules` file, so parts of the content arrive as git submodules rather than living directly in the repository.

## How to try it

```bash
git clone https://github.com/expo/skills.git
cd skills
cat skills.sh.json | head -20
```

The `.claude-plugin/` directory at the root is the Claude Code install path, and `.agents/` covers the generic agents layout. There is no npm install step to reach the skills themselves, since they are instruction files that an agent reads.

## When to use it

If you build React Native applications with Expo and you drive that work through a coding agent, these are the vendor's own notes on their own framework, which is better than a third party's guess at the API.

The grouping structure is the part to copy if you publish skills of your own. Bucketing by license and product tier, plus a manifest that a directory can index, makes a collection usable without anyone reading the repository first.

## When not to use it

The skills cover the open-source SDK and Expo's hosted services. If you are on bare React Native without Expo, most of this does not apply.

Also weigh how much is version-specific. `expo-dev-client` and `expo-module` reflect APIs that move between SDK releases, so pin to the SDK version your app is on and re-read the skills after an upgrade. The skills.sh manifest and the repository tags are where you check that.
